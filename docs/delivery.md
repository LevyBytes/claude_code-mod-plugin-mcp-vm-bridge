# Delivery and recovery

Protocol 3 uses numbered observation batches. The mod keeps the same serialized events and acknowledgements until
the relay confirms that batch. The relay caches its last response and rejects an older or changed batch. A lost
response therefore does not duplicate recorded events or turn an uncertain model submission into another prompt.

A confirmed batch is committed before dispatching its commands. Acknowledgements generated by those commands travel
in a later batch. The host can see an interim `unknown` request after a timeout; a retained acknowledgement resolves
it once delivery resumes. The host never automatically retries inference with a new request ID.

The guest's private `requests.sqlite3` records request content and outcomes. Completed entries do not occupy the active
request limit, and old request IDs still return their recorded result rather than running again. The journal is owned
by this relay; it does not import, migrate or share Claude/Codex databases. It grows with usage. Do not delete or edit
it while the relay runs; archive inactive relay state only after stopping the owned environment.

Up to 16 registrations are held in memory. When needed, disconnected registrations are retired; live registrations
are not evicted. Every replacement receives a new binding, so old controls cannot act on a new registration. Refresh
bindings after reconnecting. Pending requests are bounded separately from completed records, and interruption has
reserved queue capacity.

Recovery limits remain explicit. A relay or mod process crash invalidates bindings and may leave a command's outcome
unknown; it is not proof that no work ran. Inspect the actual Claude session and artifacts before deciding what to do.
The journal is evidence, not permission to resume work automatically. A turn abort is not proof that all child tools
or background processes stopped.

Updates freeze payload bytes, verify the exact generated file inventory, recheck source freshness after validation,
and prove host-to-guest mapping before publishing. Backups include removed files. Publication across multiple files is
not crash-atomic: do not activate an interrupted update until its backup manifest and deployed files are reconciled.
